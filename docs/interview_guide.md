# RAG 系统面试与学习指南

## 一、项目定位（30秒电梯演讲）

> "这是一个**生产级 RAG 系统**，覆盖文档摄入→多路检索→融合重排→LLM生成→自动评估全链路。
> 核心亮点是 **Dense+BM25 多路召回 + RRF 融合 + Cross-Encoder 精排** 的三级检索架构，
> 配合 **RAGAS 四维评估**和**内置 Trace 可观测性**，实现了可量化、可追踪的检索增强生成。"

## 二、系统架构全景

### 2.1 请求生命周期

```
用户问题
    │
    ▼
┌─────────────────┐
│  Query Transform │  ← Multi-Query: 生成 3 个查询变体
│  (可选)          │  ← HyDE: 生成假设性文档
└────────┬────────┘
         │ queries: [q1, q2, q3, q_original]
         ▼
┌─────────────────────────────────────────┐
│           Multi-Recall (多路召回)         │
│  ┌─────────────┐    ┌─────────────┐     │
│  │ Dense       │    │ Sparse      │     │
│  │ (Embedding  │    │ (BM25+jieba)│     │
│  │  + Chroma)  │    │             │     │
│  └──────┬──────┘    └──────┬──────┘     │
│         ▼                   ▼            │
│    top-20 docs         top-20 docs       │
└─────────────────────────────────────────┘
         │
         ▼
┌─────────────────┐
│   RRF Fusion    │  ← score(d) = Σ 1/(k + rank_i(d)), k=60
└────────┬────────┘
         │ ~30 个候选
         ▼
┌─────────────────┐
│  Cross-Encoder  │  ← (query, doc) 对 → 精排 top-5
│  Reranker       │
└────────┬────────┘
         │ top-5 docs
         ▼
┌─────────────────┐
│  LLM Generation │  ← 构建 context + prompt → 流式输出
└────────┬────────┘
         ▼
    最终回答 + 引用来源 + Trace 记录
```

## 三、核心模块深度解析

### 3.1 文档摄入管道

**文件**: `app/ingestion/loader.py` → `chunker.py` → `indexer.py`

#### 分块策略对比

| 策略 | 原理 | 适用场景 | 实现要点 |
|------|------|----------|----------|
| 递归字符分块 | 按 `\n\n` > `\n` > `。` > ` ` 层级切分 | 通用文档 | chunk_size=512, overlap=64 |
| 语义分块 | 相邻句子 embedding 余弦相似度 < 阈值处切分 | 主题频繁变化 | threshold=0.75 |

**面试话术**: "我实现了两种分块策略。递归分块适合结构规整的文档，语义分块通过计算相邻句子的 embedding 相似度来检测语义跳变点，在主题交叉的长文档上效果更好。"

#### 层级索引设计

```
L1 摘要索引 (summaries collection)
  └── LLM 为每篇文档生成 200 字摘要 → 向量化
  └── 用途：粗粒度定位相关文档

L2 明细索引 (chunks collection)
  └── 原始分块 → 向量化
  └── 用途：细粒度段落检索
```

**检索流程**: 先 L1 定位文档 → 再 L2 在目标文档内精细检索（`filter={"doc_id": {"$in": target_ids}}`）

### 3.2 多路检索

**文件**: `app/retrieval/dense.py`, `sparse.py`, `fusion.py`, `reranker.py`

#### 为什么需要多路召回？

| 检索方式 | 优势 | 劣势 | 典型场景 |
|----------|------|------|----------|
| Dense (向量) | 理解语义、同义词 | 对精确术语/编号弱 | "如何提升系统吞吐量" |
| Sparse (BM25) | 精确关键词匹配 | 无法理解语义关系 | "B+树的度是多少" |
| **混合** | **互补，提高召回率** | 需要融合策略 | 通用 |

#### RRF 融合公式

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

- `k = 60`（平滑常数，减少高排名的过度优势）
- **只用排名不用原始分数** → 避免 Dense 和 BM25 分数不可比
- 多路都命中的文档自然获得更高分数

**面试话术**: "RRF 的核心思想是只利用排名信息做融合，不依赖各路检索的原始分数。因为向量相似度是 0~1，BM25 分数可能是 0~30，直接加权没有意义。RRF 通过倒数排名来归一化，k=60 是论文推荐的经验值。"

#### Cross-Encoder vs Bi-Encoder

| 维度 | Bi-Encoder | Cross-Encoder |
|------|-----------|---------------|
| 输入 | query 和 doc 分别编码 | (query, doc) 拼接后一起编码 |
| 交互 | 无交互（余弦相似度） | 全交互（交叉注意力） |
| 速度 | 快（可预计算） | 慢（每对都要推理） |
| 精度 | 较低 | **高** |
| 用途 | 大规模初筛 | 少量候选精排 |

**面试话术**: "Bi-Encoder 快但粗，Cross-Encoder 慢但准。所以我的架构是先用 Bi-Encoder（向量检索）从几百个文档中召回 30 个候选，再用 Cross-Encoder 精排到 5 个。这样既保证了速度又保证了精度。"

#### BM25 中文分词

```python
# 使用 jieba 词级分词（非单字），过滤停用词
tokens = jieba.lcut(text.lower())
# 保留：英文/数字完整单词 + 中文≥2字的词
```

### 3.3 查询改写

**文件**: `app/retrieval/query_transform.py`

| 策略 | 原理 | 适用场景 |
|------|------|----------|
| Multi-Query | LLM 生成 3 个不同角度的查询变体 | 用户问题模糊、角度单一 |
| HyDE | LLM 生成假设性回答，用其 embedding 检索 | 问题与文档措辞差异大 |

**面试话术**: "Multi-Query 解决的是用户措辞不够精确的问题，通过生成多个不同视角的查询来扩大召回面。HyDE 解决的是问题和文档在语义空间中距离远的问题，因为假设性回答在措辞上更接近真实文档。"

### 3.4 生成模块

**文件**: `app/generation/chain.py`, `prompts.py`

#### Prompt 设计要点

```
1. 仅基于文档回答（不编造）
2. 标注来源 [来源: 文档名]
3. 信息不足时诚实拒答
4. 聚焦问题本身（不扩展）
5. 结构清晰（列表/分段）
```

#### 流式输出 (SSE)

```
event: retrieval   → 检索元数据（查询变体、各路命中数、耗时）
event: token       → 逐 token 流式输出
event: done        → 完成信号 + 来源列表 + 总耗时
```

### 3.5 评估模块

**文件**: `app/evaluation/metrics.py`

#### RAGAS 四维指标

| 指标 | 评估对象 | 含义 | 实现方式 |
|------|----------|------|----------|
| Faithfulness | 生成质量 | 回答是否忠于上下文（不幻觉） | LLM 提取声明 → 逐一验证 |
| Answer Relevancy | 生成质量 | 回答与问题的相关程度 | LLM 直接评判切题度 |
| Context Precision | 检索质量 | 相关文档是否排在前面 | 加权 Precision@K |
| Context Recall | 检索质量 | 是否检索到了所有相关信息 | 标准答案声明 → 上下文归因 |

#### 实际评估结果

**检索质量（CMRC，零 LLM，决定性指标）**：

| 指标 | 得分 | 目标 | 状态 |
|------|------|------|------|
| 命中率 | **100%（31/31）** | ≥90.32% | ✓ |
| 关键词覆盖率 | **100%** | — | ✓ |
| 平均检索耗时 | ~5.1s/题 | — | 检索（embedding+rerank）为冷查询瓶颈 |

**生成质量（RAGAS 四维，DeepSeek 生成+评判，20 题）**：

| 指标 | 得分 | 说明 |
|------|------|------|
| Faithfulness | 0.82 | |
| Answer Relevancy | 0.32 | 关思考模式后答案偏简短所致（已对照验证 judge 正常）|
| Context Precision | 0.85 | |
| Context Recall | 0.82 | |

> ⚠️ **口径 caveat**：RAGAS 基线由 qwen 生成+评判，本轮换成 DeepSeek，**不同口径不可直接对比**。
> 检索质量以与 LLM 解耦的 CMRC 评估为准（100%）；RAGAS 反映的是「DeepSeek+关思考」配置下的生成质量。
> 详见 [验证报告](./superpowers/reports/2026-07-22-task11-validation-report.md)。

**面试话术**: "我用双轨评估：RAGAS 四维（LLM-as-Judge）衡量生成质量，CMRC 命中评估（零 LLM）衡量检索质量。换 LLM 后我特意用 CMRC 这个与模型解耦的尺子来公平地证明检索接线有效——命中率 100%。同时我诚实标注了 RAGAS 的跨模型口径问题，不拿不可比的数字直接报喜。"

### 3.8 统一检索管道与并发治理（本次迭代核心）

这是本项目第二轮迭代的主体工作，包含 4 个可作为面试叙事的设计决策。

#### 决策一：把检索重构为统一的 7 阶段管道 `RetrievalPipeline`

**问题**：原本检索逻辑散落在 `chain.py` 里，查询改写、多路召回、融合、重排、CRAG 耦合在一个大方法中，难以单独测试和扩展。

**做法**：抽出 `app/retrieval/pipeline.py`，把检索定义为 7 个职责单一的阶段：

```
gate(要不要检索) → transform(查询改写) → recall(多路并行召回) → fuse(RRF)
→ rerank(精排) → evaluate(CRAG分级) → remediate(不合格则补救)
```

`chain.py` 退化为**薄编排层**，只负责「调 pipeline 拿文档 → 拼 prompt → 生成」，`retrieve()` 委托给 `pipeline.run()`。

**面试话术**：「我把检索从生成链里解耦成独立的 `RetrievalPipeline`，7 个阶段各自可测、可开关、可替换。这样 CRAG 补救这种『管道中再嵌一条小管道』的逻辑才有清晰的落点，而不是往大方法里继续堆 if。」

#### 决策二：把 5 个『半成品』特性真正接进主管道

**问题**：代码库里已有 Summary 摘要索引、CRAG 门控、CRAG 补救、Parent-Child、Graph 等模块，但大多**写了没接进主链路**（dead feature）。

**做法**：用配置开关把它们逐一接入 `RetrievalPipeline`，并补离线行为测试：

| 特性 | 接入方式 | 开关 |
|------|----------|------|
| Summary 召回 | 作为**第 5 路**参与并行召回 + RRF | `use_summary_recall` |
| CRAG 门控 | `gate()` 判断是否需要检索，可跳过检索直接生成 | `use_crag_gate` |
| CRAG 补救 | `evaluate()` 分级后，不合格走 `remediate()`（HyDE+重召回+RRF+重排）| `use_crag` |
| Parent-Child / Graph | 作为召回通道并入 `ALL_CHANNELS` | `use_parent_child` / `graph_enabled` |

**验证**：与 LLM 解耦的 CMRC 检索评估 **命中率 100%（31/31）、覆盖率 100%**。

**面试话术**：「接半成品比写新功能更难，因为要在不破坏既有行为的前提下把它们织进主链路。我用配置开关 + 离线行为测试（含 mutation testing）保证每接一个特性都可验证、可回滚。」

#### 决策三：并发治理——闸门 + 解除事件循环阻塞 + 排队超时

**问题**：`/api/chat` 是 CPU（embedding/rerank）+ IO（LLM）混合负载，高并发下会打满事件循环和下游 LLM。

**做法**：
1. **`asyncio.Semaphore` 闸门**：`max_concurrent_requests` 限制同时在途请求数（lifespan 中创建）
2. **`asyncio.to_thread`**：把同步的检索/生成放到线程池，**解除对事件循环的阻塞**
3. **排队超时 503**：`request_queue_timeout` 内拿不到闸门信号量就返回 503，快速失败而非无限堆积
4. **语义缓存**：embedding 相似度命中缓存，重复查询毫秒级返回，吸收热点负载

**面试话术**：「FastAPI 是异步的，但我的检索是同步阻塞调用，直接 await 会卡死事件循环。所以我用 `to_thread` 卸载到线程池，再用 Semaphore 做准入控制、超时返回 503 做快速失败。语义缓存则让重复查询绕过整条管道。」

#### 决策四：eval 驱动 + 测量严谨（识别跨模型混淆）

**问题**：迭代中途把 LLM 从 qwen 换成 DeepSeek，导致 RAGAS 四维「生成模型 + 评判模型」同时变化，**与历史基线不可比**。

**做法**：
1. 识别出混淆后，改用**与 LLM 解耦的 CMRC 检索评估**作为检索质量的决定性指标（命中率 100%）
2. 对 `answer_relevancy=0.32` 的异常低值做**对照实验**：用好答案测 judge 能正确打 1.0 → 证明不是 bug，而是「关思考模式后答案偏简短」的真实信号
3. 落地 **思考模式开关** `llm_thinking_enabled`（DeepSeek reasoning 模型用 `extra_body={"thinking":{"type":"disabled"}}` 关闭，避免 reasoning_content 吃掉 max_tokens）

**面试话术**：「换模型后 RAGAS 全线下跌，我没有直接报喜或报忧，而是先定位这是『换模型导致的不同口径』混淆，再用无 LLM 的 CMRC 评估给出检索质量的公平结论。评估指标本身也要被审视，不能拿来就用。」

### 3.9 RAG 2.0 深度增强（第三轮迭代核心）

**背景**：对标行业观点「RAG 1.0 三件套（调包 + 存库 + 拼 prompt）已过时」。RAG 2.0 的差距不在『有没有检索』，而在**检索层的自适应降噪与迭代、生成层的幻觉控制、评估层的端到端闭环**。本轮在三层各做深度增强，共 5 个特性，每项独立开关、异常均优雅降级到原行为。

#### F1 · Autocut 自适应截断（检索层降噪）

**问题**：重排后固定取 TopK 会把『噪声尾巴』也塞进上下文——相关文档可能只有 2 篇，TopK=5 却硬凑 5 篇，稀释信号、诱发幻觉。

**做法**：用 **Kneedle 膝点检测**动态找重排分数的『拐点』，在相关性骤降处截断：
- 重排分数 min-max 归一化 → 求各点到首尾连线的垂直距离 → 距离最大处即膝点
- 保留 `[autocut_min_docs, retrieval_top_k]` 区间：下界防截过头，上界保证不扩容
- 分数平坦（无膝点）时回退 TopK，行为不退化

**面试话术**：「固定 TopK 是个魔数，相关文档多就截掉有用的、少就放进噪声。我用 Kneedle 找重排分数的膝点自适应截断——CrossEncoder 计算量不变（只是多返回再截），却能让上下文只留『真正相关的那几篇』。」

#### F2 · Self-RAG 迭代检索（检索层，质量驱动终止）

**问题**：单轮检索证据不足时，固定 TopK 无能为力；而朴素『多检索几轮』又不知道何时该停。

**做法**：证据不足（CRAG 评为 ambiguous/incorrect）时进入有界迭代：精化查询（`QueryTransformer.refine`，基于『已有证据 + 缺口理由』生成补充查询）→ 补充召回 → 合并去重重排 → 重新评估。**终止判断是质量驱动而非资源兜底**：
1. **充分性**：CRAG 评为 correct（证据已足以回答）→ `sufficient`
2. **收敛性**：本轮精化召不到任何新增相关文档（精化已无效）→ `converged`
3. **安全兜底**：`max_retrieval_iterations` 硬上限仅防失控，**不是**主信号

**面试话术**：「迭代检索最关键的是『什么时候停』。我不是用 token 预算或固定轮数兜底，而是用两个质量信号：证据够了（CRAG correct）就停，或者精化已经召不到新东西（收敛）就停。硬上限只是防失控的保险丝，不是终止依据。」

#### F3 · 生成忠实度自检（生成层幻觉检测）

**问题**：检索 100% 准确，LLM 仍可能生成文档里没有的内容（生成层幻觉），prompt 约束根除不了。

**做法**：生成后做 **LLM-judge 忠实度校验**——从答案抽取关键论断，逐条判断是否被上下文支撑，`score = 支撑论断占比`。不忠实（`score < threshold`）则用更严格的 `STRICT_RAG_PROMPT`（信息不足必须明说『文档未涉及』，绝不补全）**有界重生成**（最多 `faithfulness_max_regen` 次）。检查异常返回 `faithful=None` 放行，不阻断主流程。

**面试话术**：「检索准 ≠ 答案准，LLM 会脑补。我在生成后加一道忠实度自检：把答案拆成论断逐条对照上下文，支撑率低于阈值就用更严格的 prompt 重生成一次。它和检索层的 CRAG 形成双层防线——CRAG 管『检索到的够不够』，忠实度管『生成的有没有超出检索到的』。」

#### F4 · 查询路由 / 类型自适应（检索层，零 LLM）

**问题**：所有查询用同一套召回策略（固定 channels/top_k/降噪强度），但数字型、对比型、多跳型查询的最优策略不同。

**做法**：规则驱动（正则/关键词，**零 LLM、确定可测**）把查询分为 numeric / comparative / multi_hop / conceptual / factual，按类型调整 `top_k`（检索深度）与 `autocut_min_docs`（降噪强度）。例如对比/多跳型提高 top_k 取更多候选，数字型收紧 autocut。优先级 numeric > comparative > multi_hop > conceptual > factual。

**面试话术**：『自适应策略』不一定要上模型。我用零 LLM 的规则路由器按查询类型调检索深度和降噪强度——确定、可测、零延迟，把『什么查询该怎么检』显式化，而不是对所有问题一刀切。

#### F5 · 端到端三层评估 harness（评估层 + A/B）

**问题**：好的 RAG 评估不只看『检索准不准』，还要看『生成好不好』和『端到端用户满意度』；且新特性到底有没有用，需要 A/B 量化而非口头宣称。

**做法**：`run_e2e_eval.py` 对 CMRC 31 题跑 `chain.invoke()` 全链路，度量**三层**：
- **检索层**：命中率 + 平均检索篇数 + Autocut 降噪幅度（`pre_autocut` vs final）
- **生成层**：忠实度（F3 提供）+ 重生成率
- **端到端**：答案 vs gold 的中文 **F1**（字符级多重集）/ **严格 EM** / **宽松命中**（gold 子串命中）

支持 `--mode baseline`（F1-F4 全关）vs `--mode full`（全开）的 **A/B**，以及 `--only Fx` 单特性归因；评估强制关闭语义缓存避免跨模式污染；增量写盘、异常优雅降级。

**面试话术**：「我做了端到端三层评估，把检索命中、生成忠实度、答案正确性分开度量，再用 A/B 把 RAG2.0 四特性整体和单个特性的边际贡献都量化出来——评估本身要能回答『这些优化到底有没有用、各贡献多少』。」

#### F6 · 答案定位增强（检索层，回应「命中率饱和但 F1 不动」）

**问题**：F5 的 A/B 诚实结论指出——检索命中率已 100% 饱和，但端到端 F1 抬不动，瓶颈是『**源文档命中了、精确答案 span 却不在 top 块**』的召回粒度问题（文章深度问题一）；同时 multi_hop 问题（答案需跨多事实拼接）单轮召回覆盖不全。F6 正面补这块短板，分两条腿：

**做法**：
- **F6a 细粒度召回 + 上下文增强**：① 把此前写了没接进主链路的 **Parent-Child** 真正接线（子块 200 字精确匹配、父块 1024 字回传上下文）；② 引入 **Contextual Chunking**（Anthropic Contextual Retrieval）——索引期用 LLM 给每个 chunk 生成文档级上下文，**embed「上下文+原文」提升可检索性，但 `page_content` 仍存原文**，所以**在线检索零 LLM 成本**；③ 用独立 Chroma 集合 `chunks_contextual` + `detail_store` 属性切换，仅在开关开且集合非空时启用，否则回退原集合（**未重建索引时行为与旧版完全一致，回归安全**）。
- **F6b 多跳查询分解**：`decompose` 把 multi_hop 问题拆成子问题，**并行优先**（各子问题轻量召回后 RRF 合并），`chain=True` 时**链式**（用上一跳证据 `refine` 出下一跳）；**仅 `query_type=="multi_hop"` 触发**，不给简单查询加分解开销。

**量化结论（2026-07-25 评估闭环，15 条多跳集）**：baseline vs full 的 F1 0.255→0.276，但**分解触发率仅 6.7%（1/15）**——规则路由对 multi_hop 的召回太低，分解收益无法有效测量。`--only F6` 实验（路由关闭）分解率为 0，**实证了"分解触发依赖路由输出"的特性依赖**：对有依赖的特性对，单特性归因法失效，必须用 baseline vs full 差值口径。下一步优化点是路由 multi_hop 规则召回或分解触发与路由解耦。

**面试话术（评估方法论加分项）**：「我扩了 15 条多跳集想量化分解收益，结果暴露了一个真问题：分解几乎不触发，因为规则路由只判出 1/15 是多跳。我再用 --only F6 对照实验证实了分解对路由的依赖——这告诉我两件事：瓶颈在路由召回不在分解器；有依赖关系的特性不能用单特性归因。评估的价值不是刷分，是暴露这种问题。」

**面试话术**：「我上一轮如实报告了『命中率 100% 但 F1 不动』，并定位到瓶颈是召回粒度——源命中不等于答案 span 进了 top 块。所以这一轮我做 F6 答案定位增强：一是把 Parent-Child 真正接进主链路并叠加 Contextual Chunking，用『索引期花一次 LLM、在线零成本』的方式让精确答案段更容易被召回；二是对多跳问题做查询分解，并行召回再融合。两个开关都默认开、异常都降级回原路径，contextual 集合为空时自动回退，保证不破坏已饱和的命中率。」

> **对应深度问题**（「embedding 高相似但答案不在召回」）：这正是 F6 要解决的——bi-encoder 的语义相似 ≠ 答案 span 命中。F6a 用更细的子块匹配 + 文档级上下文消歧提升 span 级可检索性，F6b 用分解覆盖跨段事实；评估侧新增 `answer_in_top_context`（gold 是否落在 top 上下文）直接度量这件事，而非只看源命中。

### 3.10 RAG 3.0 生产级增强（第四轮迭代核心）

**背景**：RAG 2.0 解决了「检索得准、生成不编造」；但对标**生产级 RAG**，还差六件事——答案**不可溯源**、流式**首 token 慢**、重复查询**重复算 embedding/rerank**、答案**与短答案对不齐（EM=0）**、多轮**指代未解**、以及**无指标/鉴权/限流/结构化日志**。本轮补齐这六项（F7–F12），设计准则与前三轮一致：**每项独立开关、异常优雅降级、默认路径零在线 LLM 增量（时延优先）、可离线单测**。

#### F7 · 引用溯源（生成层，零在线 LLM）

**问题**：生产级 RAG 答案必须可验证。此前只有 `[来源: 文档名]` 文本标注，定位不到具体块、无置信度。

**做法**：生成后把答案切成句子级 claim，用 **embedding 余弦相似度**（复用已有 doc 向量，**零在线 LLM**）把每个 claim 关联到最相关源块，输出结构化 `Citation{claim, source, chunk_id, doc_index, confidence, snippet}`。claim 数上限 `citation_max_claims` 控制编码量。

**面试话术**：「可溯源不能只贴个文档名。我把答案拆成句子级 claim，用 embedding 余弦把每句话挂到最相关的源块上，给出块级定位和置信度——全程零在线 LLM，只多一次批量编码。」

#### F8 · 投机流式忠实度（生成层，TTFT 优先）

**问题**：F3 忠实度自检让流式路径退化为「先整体生成+自检再吐」，TTFT≈完整生成时延，用户体验差。

**做法**：**投机流式**——先逐 token 把答案流给用户（快 TTFT），流末再跑忠实度检查；不忠实则 strict 重生成并追加 `correction` 事件替换最终答案。用户「既快、又看到已校验答案」。

**面试话术**：「忠实度检查不该卡在首屏前。我把检查移到流末：先逐 token 流出去保住 TTFT，流完再自检，不忠实就补一个 correction 事件给校验后的答案——快和可信我都要。」

#### F9 · 多级缓存（检索层，降 P95）

**问题**：相同/相似查询重复做 embedding（~50–200ms）与 cross-encoder 重排（~100–500ms），抬高 P95。

**做法**：在语义响应缓存（L3）之上新增 **L1 Embedding 缓存**（key=文本）与 **L2 Rerank 缓存**（key=`hash(query+sorted(chunk_ids))`，命中即跳过 cross-encoder）。通用线程安全 LRU，O(1)。**rerank key 含 chunk_id 集合，文档一变 key 就变，不返回过期排序。**

**面试话术**：「重排是最贵的一步。我加了 L1 embedding + L2 rerank 两级 LRU 缓存，重复查询直接省掉编码和重排。关键是 rerank 的 key 把 chunk_id 集合算进去，文档更新后 key 自动失效，不会拿到脏排序。」

#### F10 · 答案质量增强（生成层，正面打 EM=0）

**问题**：端到端 EM=0、F1≈0.35——根因是完整回答冗长、把答案埋在解释里，与短答案 span 对不齐。

**做法**（三件套，均可独立开关）：① **答案聚焦 Prompt**（要求「第一行先用一句话直接给出答案」把答案前置）；② **零 LLM 答案抽取**（数字型抽年份/数值、否则抽首个实质句，写入 `short_answer`）；③ **自适应自一致性**（仅 numeric/factual 短答案型采样 N 次投票，其余跳过保时延，默认关）。

**面试话术**：「EM=0 不是检索错，是答案没对齐——模型把『1963 年』埋在一长段解释里。我用聚焦 prompt 把答案前置，再零 LLM 抽出 short_answer。冒烟评测里 short_answer 把 EM 从 0 拉到 0.10、F1 从 0.35 拉到 0.52——证明瓶颈确实在『答案表达』而非『检索』。」

#### F11 · 可观测性与生产加固（横切）

**问题**：无指标导出、无鉴权、无限流、无结构化日志，距生产级有差距。

**做法**：① 进程内**指标注册表**（计数器/直方图，零依赖，`/api/metrics` 导出 Prometheus+JSON）；② **API Key 鉴权**（`api_key` 空即关，health/metrics 豁免）；③ **固定窗口限流**（按 IP 每分钟，超限 429）；④ **JSON 结构化日志**开关。安全中间件仅在配置开启时注册，默认关不影响测试/流式。

**面试话术**：「生产级不能只有功能。我补了指标注册表（零依赖自实现，不引 prometheus 客户端）、API Key 鉴权、按 IP 限流和结构化日志——而且做成默认关、配置开启才挂中间件，保证不拖累默认链路和测试。」

#### F12 · 多轮对话记忆（检索层，历史感知重写）

**问题**：多轮追问含指代/省略（「它的原理呢？」），直接检索会丢上下文。

**做法**：检索前用对话历史把当前问题重写为自包含查询——**零 LLM 启发式**检测指代词/省略短句并用最近一轮主题词回填；`history_rewrite_use_llm` 开启时才走一次小调用（默认关保时延）。

**面试话术**：「多轮的『它的原理呢』直接检索是检不准的。我在检索前做历史感知重写，默认用零 LLM 启发式回填指代，只有显式开启才花一次 LLM 调用——把多轮上下文补进查询，又不给默认路径加时延。」

**量化结论（2026-07-25 评估闭环，12 组多轮集）**：重写层启发式 **12/12 全命中**（触发/改写/关键词命中率均 100%）；端到端检索命中率 **0.67→0.75**，典型样本「它的解决方案有哪些？」覆盖率 0→0.60。但也测出**双刃剑效应**：话题噪声词会拉低本已可检索的样本（mt7 覆盖率 0.83→0），端到端 F1 持平——多轮收益上限由改写质量决定，LLM 重写路径是后续优化点。

**面试话术（进阶版）**：「我用 12 组多轮集量化后得到一个诚实结论：启发式重写能把『完全检不到』的指代追问救回来（覆盖率 0→0.6），但对已可检索的样本会引入话题噪声。所以我把 LLM 重写做成可开关路径，收益上限取决于改写质量——这个权衡我是用数据讲出来的。」

#### 本轮验证（CMRC 31 题，DeepSeek；详见 [RAG3.0 验证报告](./superpowers/reports/2026-07-24-rag3-validation-report.md)）

| 维度 | baseline（RAG2.0） | full（RAG3.0 全开） | 解读 |
|------|:---:|:---:|------|
| 检索命中率 | 100% | 100% | CMRC 已饱和 |
| **docs→LLM** | **8.0 篇** | **4.26 篇** | **F1 Autocut 降噪 −47%** |
| 端到端 F1（完整答案） | 0.349 | 0.352 | 完整答案仍冗长≈持平 |
| **short_answer F1（F10）** | 0.0（未抽取） | **0.520** | **答案抽取把 F1 +48%** |
| **short_answer EM（F10）** | **0.0** | **0.097** | **EM=0 被打破** |
| 生成忠实度 | 未测（F3 关） | 0.774 | F3+F8 双层，重生成 22.6% |
| 平均引用数（F7） | 0 | 1.52 | 答案可溯源到块 |
| 平均延迟 | 5.97s | 8.11s | +36%，主要来自 F3 judge（见诚实结论） |

**诚实结论（面试可直接讲）**：RAG 3.0 没有去刷一个已饱和的检索基准，而是补齐生产级能力并**正面攻击 EM=0**——F10 答案抽取把 short_answer 的 EM 从 0 提到 0.097、F1 从完整答案的 0.35 提到 0.52（+48%），证明上一轮定位的『答案表达没对齐』确实是瓶颈且可被零 LLM 后处理缓解；同时 F7 让答案平均带 1.5 条块级引用、F1 Autocut 降噪 47%、F3+F8 给出 0.77 忠实度与 22.6% 重生成。**延迟 +36% 要如实归因**：增量几乎全部来自 F3 忠实度 judge 与 F2 迭代检索（这两个是 RAG2.0 特性，baseline 把它们关了），**F7–F12 自身默认路径零在线 LLM 增量**——F9 缓存命中时 P95 反而更低。

**面试话术**：「这一轮我对着生产级 RAG 的清单补短板：可溯源、低延迟流式、多级缓存、答案质量、可观测加固、多轮记忆，共六个大特性。我最想讲的是 F10——上一轮我如实报告 EM=0 并定位到『答案表达没对齐』，这一轮用零 LLM 的答案抽取把 EM 从 0 拉到 0.10、F1 拉到 0.52，闭环了我自己提出的问题。而且所有特性默认路径都不加在线 LLM 调用，时延不掉。」

### RAG 4.0 · F13 Agentic RAG（ReAct 状态机自主检索）

**问题**：固定七阶段管道的"编排智能"到瓶颈——所有查询走同一套流程，F6b 分解触发还依赖 F4 路由判定（评估闭环实测 15 条多跳仅判中 1 条）。

**做法**：把编排决策交给 LLM 的 ReAct 循环（thought→action→observation），**概念对齐 LangGraph 但零新依赖手写**，工具复用管道阶段：`search(query)`（召回+融合+重排）/ `decompose()`（F6b 分解，**agent 自主决定，不再依赖路由**）/ `grade()`（CRAG 分级）。护栏：max_steps=4 硬上限、决策解析失败即停、工具异常写入 observation、**整体异常/空证据降级回七阶段管道**。默认关，每步 1 次 256-token 小决策调用。

**实测（15 条多跳集，--only F13 vs baseline，两次复跑）**：端到端 F1 **0.255→0.283/0.286（全场最优，优于 full 的 0.276）**，延迟约 +20%（7.8s→9.5s）。**诚实发现**：① agent 偏向过度检索（10/15 打满 max_steps）；② 工具选择高度 search 主导（52 次决策中 search 43 次、decompose 仅 3 次）且**跨运行不稳定**（首轮 decompose 0 次）——工具选择行为需要 prompt 工程（few-shot 示例/工具描述调优）引导，这是下一步优化点。

**面试话术**：「我做 Agentic RAG 时没有引 LangGraph，而是按它的概念（State/Node/条件边）手写了一个 ReAct 状态机——零新依赖、全离线 mock 测试，面试能讲清每个决策点。工具直接复用我现有管道的阶段，agent 只做编排。最有意思的是评估暴露的问题：agent 在多跳集上 F1 最高，但 10/15 打满步数上限、从不主动分解——这说明『让 LLM 当编排器』不是免费的，工具选择的 prompt 工程才是真功夫。而且降级链是完整的：agent 任何异常都落回我已验证的七阶段管道。」

**为什么不引 LangGraph（可直接讲）**：① 状态机核心（State + 节点 + 条件路由）手写仅约 200 行，依赖为零；② 离线 mock 测试不绕框架的抽象（我的 19 个测试全离线）；③ 理解原理后，知道什么时候该引框架——当状态分支变复杂、需要可视化编排/人机回环（human-in-the-loop）时，LangGraph 才是正确答案。

## 五、面试高频 Q&A

### Q1: "为什么选择 RRF 而不是直接加权分数？"

> Dense 检索的余弦相似度范围是 [0,1]，BM25 分数可能是 [0,30+]，两者量纲完全不同，直接加权没有意义。RRF 只利用排名信息，天然解决了分数不可比问题。而且 RRF 有一个很好的性质：多路都命中的文档会自动获得更高分数，不需要手动调权重。

### Q2: "Cross-Encoder 这么慢，为什么不直接用 Bi-Encoder？"

> 精度差距很大。Bi-Encoder 是 query 和 doc 独立编码，没有交互；Cross-Encoder 是拼接后做交叉注意力，能捕获细粒度的语义匹配。但 Cross-Encoder 每对都要推理一次，所以只能对少量候选用。我的架构是 Bi-Encoder 初筛 30 个 → Cross-Encoder 精排到 5 个，兼顾速度和精度。

### Q3: "查询改写不会引入噪声吗？"

> 会。所以我有三个保护措施：
> 1. 始终包含原始查询（不会被改写结果完全替代）
> 2. 多路结果经过 RRF 融合和 Rerank，噪声文档会被自然淘汰
> 3. 可以通过配置关闭查询改写（渐进增强原则）

### Q4: "如何评估 RAG 系统效果？"

> 我使用 RAGAS 框架的四维指标：
> - **Faithfulness**（忠实度）：回答是否编造了文档中没有的内容
> - **Answer Relevancy**（相关性）：回答是否切题
> - **Context Precision**（精确度）：相关文档是否排在前面
> - **Context Recall**（召回率）：是否检索到了所有必要信息
>
> 实现方式是 LLM-as-Judge，让 LLM 提取回答中的声明逐一验证。在 12 题测试集上四项指标均 >0.9。

### Q5: "中文检索效果怎么保证？"

> 三个层面：
> 1. **分词**：BM25 使用 jieba 词级分词（非单字），过滤单字停用词
> 2. **测试集**：故意设计高干扰性中文问题（如"缓存穿透/击穿/雪崩"），验证语义精准理解
> 3. **主题交叉**：同一关键词出现在多篇文档中（如"缓存"在 Redis/系统设计/Python 性能），验证抗干扰能力

### Q6: "为什么用 ChromaDB 而不是 Milvus/FAISS？"

> 项目定位是展示 RAG 工程实践，ChromaDB 的优势是零运维、本地持久化、Python 原生集成。如果是生产环境需要亿级数据，会考虑 Milvus（分布式）或 Qdrant（Rust 实现，性能好）。FAISS 没有内置持久化和元数据过滤，需要额外封装。

### Q7: "系统的瓶颈在哪里？怎么优化？"

> 通过并发 bench 的瓶颈分析（冷查询，并发=1）：
> 1. **检索阶段是主要瓶颈**（~5s，占总延迟 84%）：本地 embedding + cross-encoder rerank 是 CPU 密集计算，rerank 尤其耗时
> 2. **生成阶段**（~1s）：DeepSeek 关思考模式后较快，已用流式输出优化体感
>
> 已落地的优化：
> - **语义缓存**：重复查询命中缓存，P95 从 ~8.9s 压到 ~53ms（bench 实测）
> - **多路召回并行**：线程池并发执行 5 路召回（`recall_max_workers`）
> - **to_thread 卸载**：同步检索不阻塞事件循环，保证高并发吞吐
>
> 进一步优化方向：reranker 蒸馏/量化、embedding 批处理、GPU 加速、热门查询预热。

### Q8: "如果让你重新设计，会怎么改？"

> 已经做了的（第二轮迭代）：
> - **Graph RAG**：零 LLM 快速构建知识图谱，实体多跳召回（作为召回通道之一）
> - **Parent-Child / CRAG 门控与补救 / 语义缓存**：均已接入统一管道
>
> 下一步想做的：
> 1. **自适应检索**：根据 query 复杂度动态决定是否改写、是否多路、是否精排（CRAG 门控是雏形）
> 2. **Agentic RAG**：引入 Tool-Use Agent，支持多步推理与迭代检索
> 3. **检索延迟优化**：reranker 蒸馏/量化、GPU 加速（当前冷查询瓶颈在 rerank）
> 4. **向量库升级**：迁移到 Qdrant/Milvus 支持规模化
> 5. **评估闭环**：线上反馈 → 自动标注 → 策略迭代

### Q9: "embedding 高相似，但答案不在召回里，怎么办？"（RAG2.0 深度问题一）

> 这是我在端到端测试里真实遇到的（如 id=2「安室奈美惠」、id=4「除米象做法」）：source_hit 命中了文档，但**承载答案的具体片段没进 top 块**，模型只能如实说「未提及」。
>
> 我的应对与认知：
> - **多路召回 + RRF** 已降低单路 embedding 的盲区（BM25 精确词匹配能补 embedding 的语义漂移）；
> - **F2 迭代检索**在证据不足时精化查询补充召回，是『一次召回不够就再召一次』的机制；
> - 但**根因常在分块粒度**：答案 span 被切散或排在 top 块之外。这不是排序/降噪能解决的，需要 Parent-Child（小块命中、大块返回）或更细的分块策略。
> - **诚实态度**：我在报告里把它标为『当前局限』，而不是假装 F1-F4 解决了它——排序降噪和生成忠实本就不在召回粒度的作用域。

### Q10: "检索都对了，LLM 还是编造，怎么防幻觉？"（RAG2.0 深度问题二）

> 检索 100% 命中 ≠ 答案正确，LLM 会脑补文档里没有的内容。我做了**双层防线**：
> - **检索层 CRAG**：管『检索到的够不够』——不够就补救/迭代；
> - **生成层 F3 忠实度自检**：管『生成的有没有超出检索到的』——把答案拆成论断逐条对照上下文，支撑率低于阈值就用更严格的 prompt（信息不足必须明说『文档未涉及』）**有界重生成**。
>
> 实测：忠实度 0.80，22.6% 的答案触发了重生成；口语化测试里 5 个不可答问题（手机号、2099年、天气…**全部零幻觉诚实拒答**。关键是——检查异常时返回 `faithful=None` **放行不阻断**，自检是增强不是单点故障。

### Q11: "迭代检索什么时候停？会不会无限循环或浪费 token？"（RAG2.0 深度问题三）

> 我用**质量驱动终止**，不是 token 预算或固定轮数兜底：
> 1. **充分性**：CRAG 评为 correct（证据够了）→ 停（`sufficient`）；
> 2. **收敛性**：本轮精化召不到任何**新增**相关文档（精化已无效）→ 停（`converged`）；
> 3. **安全兜底**：`max_retrieval_iterations` 硬上限仅防失控，**不是主信号**。
>
> 实测 31 题：`sufficient 24 / converged 6 / max_iterations 1`，平均迭代 0.065 轮——多数首检即充分，少数才迭代，硬上限只触发了 1 次。终止判断本身要看『证据质量有没有改善』，而不是『花了多少预算』。

### Q12: "答案怎么证明不是编的？能给到出处吗？"（RAG3.0 可溯源）

> 两层防线：**F3 忠实度自检**（生成后拆论断逐条对照上下文，不忠实严格重生成）管『有没有超出检索到的』；**F7 引用溯源**（把答案切句子级 claim，用 embedding 余弦挂到最相关源块）管『每句话出自哪个块』，给出 `chunk_id + 置信度 + snippet`，**零在线 LLM**。前端可点引用跳到原文块。

### Q13: "你上一轮说 EM=0，这一轮怎么解决的？"（RAG3.0 自我迭代）

> 我先定位再下药：上一轮 A/B 证明检索已 100% 命中、F1 抬不动，瓶颈是『**答案表达没和短答案对齐**』（模型把『1963 年』埋在长解释里）。这一轮 F10 用**答案聚焦 prompt + 零 LLM 答案抽取**把 `short_answer` 抽出来——冒烟/全量评测里 short_answer 的 **EM 从 0 → 0.097、F1 从 0.35 → 0.52**。这是我『如实报告问题→定位根因→下一轮闭环』的自我迭代证据，而不是换个基准刷分。

### Q14: "加了这么多特性，延迟会不会爆？"（RAG3.0 时延预算）

> 不会，因为我把**时延预算**当设计约束：F7/F9/F10/F11/F12 默认路径**零在线 LLM 增量**（引用走 embedding、缓存命中省算、答案抽取是纯函数、指标是内存计数、重写走启发式）；F8 把忠实度检查**移到流末**反而降 TTFT；唯一可能加 LLM 的 F10 自一致性和 F12 LLM 重写**默认关闭**。所以默认配置延迟与 RAG2.0 同量级（~8s），命中缓存时 P95 还更低。

> ① 路由 multi_hop 规则召回（多跳集 15 条仅判中 1 条，F6b 分解无法触发）或分解触发与路由解耦；
