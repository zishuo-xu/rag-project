## 2. F12 多轮：量化结论

### 重写层（离线，零 LLM）

启发式路径 **12/12 全通过**：触发率 100%、改写率 100%、`rewrite_gold` 关键词命中率 100%
（pronoun 6/6、ellipsis 5/5、mixed 1/1）。报告：`data/eval_rewrite_heuristic.json`。

### 端到端（baseline vs --only F12，12 组）

| 指标 | baseline | F12 | Δ |
|---|---|---|---|
| 检索命中率 | 0.667 | **0.750** | **+8pp** |
| 端到端 F1 | 0.297 | 0.291 | ≈持平 |
| answer_hit | 0.0 | 0.0 | — |
| rewrite 触发率 | 0 | 1.0 | — |

### 诚实归因：启发式改写是双刃剑

- **正例 mt1**：「它的解决方案有哪些？」baseline 覆盖率 **0**（无实体根本检不到）→ F12 改写为
  「Redis缓存穿透解决方案有哪些？」覆盖率 **0.60**，F1 0.095→0.221。这是 F12 的核心价值场景。
- **反例 mt7**：原问题 baseline 覆盖率 0.83 已可检索，改写后话题噪声词串入
  （「Docker镜像和容器有什么区别数据持久化怎么做？」）覆盖率跌到 **0**。
- 结论：**多轮收益的上限由改写质量决定**。零 LLM 启发式解决了"完全检不到"的硬伤场景，
  但对已可检索的样本会引入噪声。LLM 重写路径（已内置、默认关）是下一步的优化点。

## 3. F6b 多跳：量化结论与一个真发现

### 端到端（15 条：baseline / full / --only F6）

| 指标 | baseline | full | --only F6 |
|---|---|---|---|
| 端到端 F1 | 0.255 | 0.276 | 0.260 |
| 检索命中率 | 0.80 | 0.80 | 0.80 |
| **分解触发率** | 0 | **6.7%（1/15）** | **0** |
| 路由分布 | n/a | multi_hop 仅 1/15 | n/a |

### 真发现：瓶颈在路由召回，不在分解器

1. F4 规则路由在本多跳集上**只判出 1/15 为 multi_hop** → F6b 分解几乎不触发，收益无法测量。
2. `--only F6` 实验（路由关闭）分解率为 0，**实证了设计评审时预判的交互**：分解触发依赖路由输出。
   单特性归因法对"有依赖关系的特性对"失效，这类特性必须用 baseline vs full 差值口径。
3. 下一步明确：提升路由 multi_hop 规则召回（如"分别/各自/哪一年…同时"等模式），
   或将分解触发与路由解耦（分解器自带可触发性判断）。

## 4. 口径与局限（诚实记录）

- 样本量小（15/12），跨模式 ±5pp 内的差异不具备统计意义；结论以方向性 + 逐条归因为准。
- 多轮集 gold 为长枚举式答案，`answer_hit`（子串严格命中）天然为 0，以 F1 + 检索覆盖率为准。
- 单次运行 + LLM 非确定性；多轮 F1 的 ±0.006 应读作"持平"而非"回退"。
- 多跳/多轮评估共用同一 Chroma 索引（sample_docs 以 tmp 副本上传），`metadata.source`
  指向 `data/` 下原始文件仅用于完整性校验，`source_hit` 口径对 tmp 副本不命中，检索判定以覆盖率为主。
