## 文章二:《我给 Agent 看了所有收敛信号,它的表现反而更差了》

**平台**:知乎(主发,叙事+反直觉结论适合知乎)→ 掘金同步
**为什么**:"信号可见 ≠ 决策控制"是强观点,适合知乎的讨论生态;三轮迭代含一轮失败,故事性最强。

**标题候选**:
1. 我给 Agent 看了所有收敛信号,它的表现反而更差了(推荐,反直觉钩子)
2. 提示词管不住 LLM 的停止决策:finish 率 33%→93% 的三轮迭代
3. 让 LLM 学会停止:一个零 LLM 硬门控的设计记录

**摘要(≤120 字)**:
我的 ReAct agent 打满步数才肯停,finish 率只有 33%。第一轮加硬约束,工具选择修好了,停止没修好;第二轮把所有收敛信号摊给它看,finish 率不升反降。这轮失败逼出一句话:信号可见 ≠ 决策控制。第三轮我把停止权从 LLM 手里拿过来,交给一个零 LLM 的证据判据——finish 率 93%,还意外收获了检索命中的跳升。

**标签**:Agent、ReAct、LangChain、RAG、LLM应用

**配图建议**:finish 率三轮变化柱状图(33→47→40→93)+ 硬门控代码片段截图。

**互动引导(知乎结尾)**:抛问题——"你遇到过哪些'给模型看信息 ≠ 能控制模型行为'的场景?"

## 文章三:《先吐为敬:我给 RAG 加了一个会"插播更正"的直播员》

**平台**:掘金 + 知乎双发(短小、通俗、技术点清晰,两平台都适合)
**为什么**:直播类比通俗,投机执行的系统设计视角有深度,篇幅最短,适合作为引流款。

**标题候选**:
1. 先吐为敬:我给 RAG 加了一个会"插播更正"的直播员(推荐)
2. 我给 RAG 加了一个正确的功能,然后体验死了
3. 从 CPU 分支预测偷来的流式 RAG 设计:先交付,后校验,错了再更正

**摘要(≤120 字)**:
给流式 RAG 加忠实度校验,最自然的接法会让首字时延等于完整生成时延——正确的功能杀死了体验。这篇讲一个从 CPU 分支预测偷来的思路:先按"它是对的"逐字交付,流末校验,不忠实插播更正。97% 的请求白赚秒开;代价也讲到底:3% 的情况里用户会先看到一秒钟未校验的答案,以及为什么这个价签必须贴着。

**标签**:RAG、流式输出、SSE、系统设计、LLM

**配图建议**:录播 vs 直播的时序对比图(文内已有文字版,画成图)+ token/correction/final 事件流示意。
