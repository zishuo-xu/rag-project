## 文章一:《RAG 特性归因:我如何证明一个优化"真的"有效——含三份无效结果》

**平台**:掘金(主发)→ InfoQ 投稿 → 知乎专栏(同步)
**为什么**:方法论 + 工程纪律,掘金/InfoQ 受众吃这套;"无效结果"是差异化钩子。

**标题候选**:
1. RAG 特性归因:我如何证明一个优化"真的"有效——含三份无效结果(推荐,诚实钩子)
2. 13 个 RAG 特性,我砍掉了自己最喜欢的一个:一条 A/B 归因纪律
3. 你的 RAG 优化真的有效吗?一份含负面结果的归因实践

**摘要(平台描述,≤120 字)**:
给 RAG 加了十个特性,指标涨了——是哪个特性的功劳?可能都不是。这篇讲一套归因纪律:独立开关、干净对照、容差设计、口径一致,以及三份我如实写进报告的无效结果(Graph RAG 升级 F1 −0.004、多跳分解收益在方差内、生成侧 prompt 两轮阴性)。负面结果不是包袱,是正面结果可信度的来源。

**标签**:RAG、LangChain、A/B测试、工程实践、检索增强生成

**配图建议**:A/B 对照表格截图(延迟 −50% 那张)+ 归因四纪律的流程图。

## 文章二:《让 LLM 学会停止:一个 Agentic RAG finish 率从 33% 到 93% 的三轮迭代》

**平台**:知乎(主发,叙事+反直觉结论适合知乎)→ 掘金同步
**为什么**:"信号可见 ≠ 决策控制"是强观点,适合知乎的讨论生态;三轮迭代含一轮失败,故事性最强。

**标题候选**:
1. 让 LLM 学会停止:Agentic RAG 的 finish 率从 33% 到 93%,我走了三轮(含一轮失败)(推荐)
2. 我给 Agent 看了所有收敛信号,它的表现反而更差了
3. 提示词管不住 LLM 的停止决策:一个硬门控的设计记录

**摘要(≤120 字)**:
我的 ReAct agent 在多跳问答上 F1 最高,但三分之二的查询打满步数上限才停。第一轮加 prompt 约束,工具选择修好了,停止没修好;第二轮让收敛信号完全可见,finish 率不升反降。这篇记录我如何从两轮失败里推出"信号可见 ≠ 决策控制",并用一个零 LLM 的证据硬门控把 finish 率从 33% 拉到 93%。

**标签**:Agent、ReAct、LangChain、RAG、LLM应用

**配图建议**:finish 率三轮变化柱状图(33→47→40→93)+ 硬门控代码片段截图。

**互动引导(知乎结尾)**:抛问题——"你遇到过哪些'给模型看信息 ≠ 能控制模型行为'的场景?"

## 文章三:《先吐为敬:RAG 流式输出如何既秒开又不出错》

**平台**:掘金 + 知乎双发(短小、通俗、技术点清晰,两平台都适合)
**为什么**:直播类比通俗,投机执行的系统设计视角有深度,篇幅最短,适合作为引流款。

**标题候选**:
1. 先吐为敬:RAG 流式输出如何既秒开又不出错(推荐)
2. 质量校验会杀死流式体验?投机流式:一个明码标价的权衡
3. 像直播一样做 RAG:投机流式的设计与那 3% 的代价

**摘要(≤120 字)**:
给流式 RAG 加忠实度校验,朴素做法是"生成完→校验→再吐给用户",首字时延等于完整生成时延,流式体验归零。这篇讲投机流式:先逐字吐给用户,校验放在流末,不忠实再插播更正——像直播而非录播。重点是那个明码标价的代价:约 3% 的请求里,用户会先看到一秒未校验的答案。

**标签**:RAG、流式输出、SSE、系统设计、LLM

**配图建议**:录播 vs 直播的时序对比图(文内已有文字版,画成图)+ token/correction/final 事件流示意。
