# RAG 特性归因:我如何证明一个优化"真的"有效——含三份无效结果

> 大多数 RAG 技术文章只讲有效的部分。这篇讲方法论:怎么让"有效"这个结论本身可信,以及当结果是无效时,你该怎么办。所有数字来自一个开源的中文 RAG 教学样板(13 项特性、300 题 CMRC 评测集、420 个离线测试),负面结果全部留档。

## 一个尴尬的事实:你可能不知道哪个特性在起作用

RAG 系统很容易长成这样:autocut、多路召回、重排、忠实度校验、引用溯源、Agentic……十几个特性叠在一起,端到端指标确实不错。但有人问"如果砍掉其中三个会怎样",你答不上来。更糟的是,其中某个特性可能早就在拖后腿,只是被其他特性的收益盖住了。

我给自己的项目定的规矩是:**每条特性一个独立开关,每个开关一份 A/B 归因数据,负面结果和正面结果用同一种格式写进报告。** 这套规矩跑下来,我拿到了几个让自己不舒服的结论——正是这些不舒服的结论,让剩下那些正面结论变得可信。

## 方法论:归因的四个纪律

**纪律一:开关必须独立且默认路径延迟中性。** 13 项特性各有布尔开关(`use_autocut`、`use_faithfulness_check`……),失败自动降级回基线行为。关键设计是默认路径零在线 LLM 增量:重活(上下文增强、图谱)放在索引期,线上判断尽量复用 reranker 分数和规则。这样"A/B 只差一个开关"才成立,而不是改一个开关带出三处隐式依赖。

**纪律二:评测分层,各层干各层的事。**

| 层 | 规模 | 耗时 | 职责 |
|---|---|---|---|
| 零 LLM 检索评测 | 300 题 | 秒级 | 改检索层即跑, hit/coverage |
| 50 题快速切片 | 50(确定性抽样) | ~4 分钟 | 日常迭代 A/B |
| 多跳/多轮切片 | 15 / 12 | ~2 分钟 | 专项能力 |
| 全量基线 | 300 | ~20 分钟 | 发版前 + 基线重定 |

**纪律三:给 LLM 非确定性留容差,而不是假装它不存在。** 质量门对端到端 F1 设 ±0.05 容差、hit 设 ±0.08——低于容差的"退化"判通过,因为那是模型抖动不是代码退化。没有容差的门是误报工厂,有容差但没有基线的门是摆设。

**纪律四:口径纪律。** 评测输出落盘时记录 provider 字段。我踩过这个坑:deepseek 和 qwen 跑出来的 F1 差 0.11,换模型的跑批和换代码的跑批混在一起比,归因就全是假的。现在基线文件、报告表格全部标口径,跨 provider 不直接互比。

## 三份无效结果(以及它们为什么值钱)

### 无效结果一:Graph RAG 升级,F1 −0.004

我把零 LLM 的 jieba 共现图升级成 LLM 类型化三元组(人/作品/地点/职位类型 + 100% chunk 溯源)。结构上这是一次明确的能力升级。代价:全量图重建 3.6 小时、约 2782 次 LLM 调用。

评测结果:F1 **−0.004**(波动带内),检索 hit/coverage 持平,延迟 +12%。三次复跑,结论稳定:**结构能力升级了,检索收益没有兑现。**

正确的做法不是藏起这个数字,而是把它当成决策输入:3.6h 的重建成本意味着任何 clone 这个项目的人都要付同样的成本——它与"可复现"这个硬目标直接冲突。于是我回退到零 LLM 共现图(1 秒重建),把类型化版本留作可选路径,报告里如实写:"关系无类型化、实体含 jieba 噪声,但检索仍可用、1 秒可复现。"

**负面结果的价值:它替"不做什么"提供了证据。** 没有这个 −0.004,我可能会在一个没有收益的方向上继续投入。

### 无效结果二:F6b 多跳分解,收益在方差内

多跳分解 + 路由修复后,F1 从 0.276 到 0.289(+0.013)。听起来是正的?但负对照的单样本波动达到 +0.275——**+0.013 完全在噪声里**。报告里我没有写"F6b 有效",写的是"弱正/方向性,幅度在方差内"。

承认"我不知道它有没有用"比硬讲一个 +0.013 的故事需要更多勇气,但读者不傻。

### 无效结果三:生成侧 prompt,两轮阴性

端到端 F1 0.60 是系统唯一短板。诊断显示瓶颈在生成侧(检索命中率 1.0,正确材料 100% 在上下文里),于是我做了两轮生成 prompt 重构实验。结果:两轮都没有显著提升。

报告结论直接写成"**生成侧残差天花板,短期无已知空间**",列为开放项而不是待办。后来用零成本失败模式诊断脚本验证了这个判断:33% 的失败题是"gold 在上下文里但抽错实体归属"——这是模型阅读理解能力问题,不是 prompt 措辞问题。诊断数据反过来解释了为什么 prompt 实验会阴性。

## 一次正面归因长什么样

有了上面的铺垫,看一个正面的:7/28 的"零 LLM 均衡化"(把热路径上的 CRAG 门控/分级、multi_query 改写从 LLM 改成规则/分数)。

改完我沒有直接宣布"优化成功",而是搭了一个受控 A/B:同一个索引、同一批 60 题、同一个 deepseek,只换代码——旧代码(git worktree 检出精简前的提交)对上新代码:

| 指标 | 精简前 | 精简后 | Δ |
|---|---|---|---|
| 平均延迟 | 7533ms | 3747ms | **−50%** |
| 检索 hit | 0.983 | 1.000 | +0.017 |
| 端到端 F1 | 0.547 | 0.577 | +0.030 |
| 端到端 EM | 0.083 | 0.136 | +0.052 |
| 忠实度 | 0.979 | 0.962 | −0.017 |

严格地说,n=60 下 ±0.05 属方差,质量结论应该读作"无显著差异、方向全正",而不是"质量提升"。我在报告里就是这么写的。但延迟 −50% 是结构性的(摘掉了两次 LLM 往返),不需要谦让。

同时我如实登记了反方向的信号:忠实度 −0.017、重生成率 1.7%→3.4%——虽然都在方差内,但它们与"无损"叙事方向相反,列出来,标注"若后续复现同向偏移需校准阈值"。

**这份 A/B 让我敢说"零 LLM 化没有牺牲质量"——不是因为结果漂亮,是因为对照是干净的。**

## 一个差点骗到我自己的陷阱

300 题复刷后,F1 0.600,比旧基线(n=100)的 0.691 低了 0.09。第一反应:退化了?

查下去:旧基线是 100 题精选集;同一个 300 题运行里,前 128 题均值 F1 0.735,后 172 题约 0.50——**题间难度本身不均**。不是代码退步,是数据集扩容稀释。如果我没做这一步核对,就会拿一个"退化"去修一个不存在的 bug,或者更糟,悄悄不提这个数字。

教训:**基线必须和评测集同寿命。** 换集就要重定基线,这个动作现在写进了 README 的复现链。

## 结语:负面结果是信用额度的来源

一个只报喜的项目,它的喜报是打折的——读者会自动打折,面试官更会。而一个把 Graph RAG 的 −0.004、F6b 的"方差内"、生成侧的"天花板"都写在明处的项目,它说"延迟 −50%、检索饱和 1.0"的时候,你不需要打折。

归因方法论没有什么秘密:独立开关、干净对照、容差设计、口径一致、以及——**愿意让数据否决自己喜欢的特性**。最后一条最难,也最值钱。
