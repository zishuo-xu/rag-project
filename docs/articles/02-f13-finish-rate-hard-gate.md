# 我给 Agent 看了所有收敛信号,它的表现反而更差了

> 一个 Agentic RAG 的 finish 率从 33% 到 93% 的三轮迭代。中间有一轮,我把所有收敛信号都摊给 LLM 看,finish 率不升反降。那轮失败比最后的成功更值钱——它告诉我:提示词能影响偏好,但不能强制决策。

## 一、先看一条失控的现场

我的 RAG 系统有一条 Agentic 路径:一个零依赖手写的 ReAct 状态机,agent 自己决定检索什么、要不要把问题拆开、什么时候停。工具复用现有管道的阶段——`search`(召回+融合+重排)、`decompose`(多跳分解)、`grade`(评估证据)、`finish`(结束),护栏是 max_steps=4 的硬上限。

在多跳问答评测集(15 题)上,它的 F1 是四种模式里最高的。但第一次跑完,日志给了我另一幅画面:

```
step 1: search("范廷颂 总主教 任命")     → 5 篇证据,含答案线索
step 2: search("范廷颂 担任 总主教 年份") → 3 篇新增,基本重复
step 3: search("范廷颂 总教区 职务")     → 1 篇新增
step 4: 已达上限,强制停止                 → finish? 从未发生
```

15 题里只有 5 题是 agent 主动 finish 的。**三分之二的查询,是撞墙停的,不是想停的。** 平均 3.5 步,search 被调用 43 次,而真正有用的检索往往第一步就完成了——剩下的步数,agent 在用不同的措辞反复搜索同一个意思。

问题很清楚:停止决策失控。

## 二、第一轮:把提示词写硬——修好了一半

最直觉的修法是教它。我在决策 prompt 里加硬约束:"需组合两个及以上事实时**优先 decompose**"、"已有 ≥1 篇相关证据**立即 finish**"、"禁止重复或语义雷同的查询",再配两条 few-shot 示例(单事实:search→finish;双事实:decompose→finish)。

复测,结果劈成两半:

- **工具选择被修好了**:decompose 触发从 3 次跳到 13-14 次,稳定复现;F1 0.286→0.298;
- **停止决策没被修好**:主动 finish 5/15→7/15(47%),仍不过半,8-12/15 的查询依然打满四步。

这个"一半好一半坏"的结果,当时让我停了一下。同一次 prompt 修改,为什么能校正工具选择,校正不了停止?

答案后来才完全想通,但这里已经露出了线索:**"该用哪个工具"是一个偏好问题——把 decompose 的条件写清楚,模型在采样时倾向于选它;而"该不该停"是一个决策问题——finish 每一轮都在和 search 竞争,而 search 永远看起来"还能再查点东西"。** 提示词能挪动概率分布,不能给分布加一条硬边界。

当时我没想透这一层,只是记下了现象,然后顺着直觉走了第二步——正是这一步,撞上了整个迭代里最值钱的一次失败。

## 三、第二轮:让信号完全可见——然后它更差了

我当时的推理是这样的:agent 不肯停,可能是因为它**不知道自己已经查够了**。看它的决策上下文,确实贫乏——每步新增了几篇证据,算出来了但没给它看;证据质量如何(CRAG 分级),从不进 prompt;走到第几步、还剩几步预算,它也一无所知。

一个信息充分的理性 actor,看到"连续两步零新增"就该收敛。于是我做了四件事,全部零新增 LLM 调用:

1. 步数预算可见:决策上下文加"第 i/N 步"和"末步必须 finish"规则;
2. 新增量可见:每个 search 的观察结果加前缀 `[新增N篇/累计M]`;
3. 证据状态可见:`共N篇｜grade=X｜连续K步零新增` 直接摊在证据摘要里;
4. 空手 finish 驳回一次:没证据就想停?驳回,给你一次纠错的机会。

预期:信号到位,agent 自然早停,finish 率上升。

**实测:延迟 12.5s→9.7s,降了 23%——agent 确实少做了无效检索。但 finish 率:40%、33%,两轮复测,不升反降。**

信号全可见了,它看得懂"零新增",于是少搜了几次(延迟降了);但"少搜"和"肯停"是两回事——它只是更快地走到最后一轮,然后照旧不打 finish。

## 四、为什么给 LLM 看信息,控制不了 LLM 的决策

这轮失败逼出了一个我至今受用的结论:

> **信号可见 ≠ 决策控制。可观测性告诉你系统在做什么,但它不强制系统做任何事。**

展开讲,这里有三个层次:

**第一层:LLM 是策略生成器,不是控制器。** 每一步,决策 LLM 在 prompt 定义的分布上采样一个动作。信号改变的是分布的形状(让 finish 的概率高一点),但只要 search 的概率不是 0,"继续搜"就会以稳定的频率发生。你无法用文本把一条规则变成物理定律。

**第二层:信息充分不等于停止有理。** 对一个被训练得"有帮助"的模型,多检索一步的期望价值在它看来几乎总是正的——万一下一篇就有更好的答案呢?收敛信号告诉它"边际收益在递减",但递减不等于零。没有哪个模型会仅凭"递减"主动终止一个被鼓励"尽量充分"的任务。

**第三层:我把两个不同的问题当成了同一个。** 延迟降了 23% 说明信号可见**是有用的**——它优化了 agent 的检索效率。但我要的不是"更高效的 agent",我要的是"一个会停的 agent"。这是效率问题和控制问题,我拿效率问题的解法去治控制问题的病,药不对症。

想通这点之后,备选方案排开比较,答案几乎是唯一的:

| 方案 | 机制 | 否决理由 |
|---|---|---|
| 收紧步数上限(4→2) | 更早撞墙 | 治标:墙还是墙,多跳题需要 2 步以上会被误伤 |
| 重复查询去重强制停 | 发现雷同查询就停 | 治标:只处理"重复搜"症状,agent 换个措辞就绕过去了 |
| 裁判判停(每步加一次 LLM 评估) | 让另一个 LLM 判断该不该停 | 每步 +1 次 LLM 调用,延迟和成本双输;而且把一个不可靠的决策交给了另一个概率组件 |
| **证据充分度硬门控** | 机器可计算的充分性判据,满足即强制 break | **停止权从概率组件移交给确定性判据** |

最后一行的关键词是**确定性**。前三条都还在概率世界内部打转——用更狠的提示词、更多的采样、另一个 LLM 去约束 LLM。第四条跳出了这个层面:**该停不停,那就别让它决定停不停。**

这也对应控制论里最基本的分工:策略组件负责"做什么",控制组件负责"什么时候必须怎样"。我前两轮的错,是让策略组件兼了控制组件的活。

## 五、硬门控:一个零 LLM 的判据怎么设计

系统里恰好有一个现成的、机器可计算的证据充分性信号:CRAG 分级。它取 top1 文档的 rerank 分数做 sigmoid 归一化,`p≥0.5` 判 correct(证据充分)——零 LLM,一次浮点运算。

门控逻辑几乎就是接线:

```python
# search/decompose 带来新证据后:
if step.action in ("search", "decompose") and new_count > 0 and settings.agentic_evidence_gate:
    sufficient, grade = self._evidence_sufficient(question, evidence)
    if sufficient:
        result.stop_reason = "evidence_sufficient"
        break

def _evidence_sufficient(self, question, evidence):
    # 累积证据按 rerank 分降序(CRAG 看 top1,顺序是契约)
    scored = [(float(d.metadata["rerank_score"]), d) for d in evidence
              if isinstance(d.metadata.get("rerank_score"), (int, float))]
    if not scored:
        return False, ""   # 无真实分数 → 不启用(见下文陷阱二)
    scored.sort(key=lambda x: x[0], reverse=True)
    grade, _, _ = self._pipeline.evaluate(question, [d for _, d in scored])
    return grade == "correct", grade
```

三个设计决定,每个都有代价:

**为什么用 sigmoid 而不是原始分数?** cross-encoder 的 logit 没有直观阈值(不同模型、不同语料的分布完全不同),sigmoid 把它压到 (0,1),阈值才可解释、可迁移。代价是:**0.5/0.3 这两个阈值是按当前 reranker(bge-reranker-base)的分数分布校准的**。换模型必须重校准——这不是 bug,是"用分数做判据"这类设计的固有契约,我在代码注释和架构文档里都写了警告。

**为什么只看 top1,不看平均?** 充分性回答的问题是"最好的证据够不够",不是"平均够不够"。一个完美命中的文档 + 九个噪声,平均分会说"不够",top1 会说"够"——后者才是生成需要的。

**两个差点踩进去的陷阱**,都是实测发现的:其一,累积证据来自多步检索,顺序是乱的,而 CRAG 的 top1 判级依赖降序输入——不排序就把噪声文档送到了判官面前;其二,decompose 的合并结果走纯 RRF、没有 rerank 分数,而 CRAG 对无分数输入"默认通过"——不显式拦截,门控就会在每次分解后无脑放行。这两处都写在代码里,是"复用现成信号"省事的代价:信号不是为你这个场景设计的,边界要自己焊。

## 六、意外的礼物:早停不只是省延迟

复测(同 15 题多跳集):

| 指标 | 第二轮最佳(纯信号版) | 硬门控版 |
|---|---|---|
| finish 率 | 53%(8/15) | **93%(14/15,evidence_sufficient)** |
| 平均步数 | 3.6 | 1.53 |
| 检索 hit | 0.80(四轮迭代从未动过) | **0.93** |
| F1 / EM | 0.291 / 0 | 0.566 / 0.133 |
| 延迟 | — | 5.9s |

finish 率在意料之中,但**检索 hit 从 0.80 跳到 0.93 是意外**。这个跳幅远超"少搜几步"能解释的范围——它逼着我追问机制,结论比门控本身更有意思:

agent 打满四步时,每一步 search 都往证据池里堆文档,其中大量是弱相关的。收尾时 rerank 从一个**被污染的池子**里挑 top_k——噪声文档会挤掉正确答案。硬门控让 agent 带着第一批高质量证据就离场,池子干净,top_k 里留下正确答案的概率反而高了。

**早停不只是省了延迟,它是一次降噪。** 这个机制是事后分析出来的,不是设计出来的——又一次提醒我:系统的真实因果链,经常藏在指标的意外移动里。

诚实的边界必须说:n=15,单次运行,±5pp 内本无统计意义;0.291→0.566 的幅度远超方差,但同期还有语料扩容和 CRAG 零 LLM 化在生效,无法把全部收益单独归给硬门控。报告里写明了全部混血因素——我在这轮迭代里学到的最重要的一件事就是,不干净的归因不配叫结论。

## 七、可以带走的一般原则

回到那句话:**信号可见 ≠ 决策控制。**

它远不止适用于 LLM。你的服务加了指标大盘,错误率依然会在某个深夜飙升——可观测性让你**看见**,熔断器才让它**不发生**;你给模型看了所有收敛信号,它依然打满步数——遥测让你**理解**行为,门控才**约束**行为。每次遇到"我已经告诉它了啊"的困境,值得问一句:我是在提供信息,还是在实施控制?

以及一个更通用的模式:**当一个概率组件反复违反某个不变式时,不要更狠地提示它,把不变式移到组件外面去。** CPU 不会"提示"分支预测器要猜对,它用验证和回滚;我的 agent 不会"读懂"收敛信号,我用一个浮点数判据替它做了停不下来的那个决定。

最后说点不那么技术主义的:这三轮里,最让我有底气的不是 93% 这个数字,是第二轮的失败。如果第一轮提示词生效了,我会带着一个错误的因果模型("finish 率是 prompt 问题")继续做下一个特性;是那轮不升反降的数据,把"信号可见 ≠ 决策控制"这句话刻进了我的工程直觉。**失败的实验只要测得干净,就不是成本,是资产。**
