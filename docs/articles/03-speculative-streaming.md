# 先吐为敬:RAG 如何既秒开又不出错——投机流式的设计与代价

> 给 RAG 加忠实度校验,会杀死流式体验;要流式体验,就得不到校验。这篇讲我如何用"投机执行"的思路打破这个二选一——以及这个设计明码标价的代价:答案被看见的那一刻,它还没过完校验。

## 质量特性会吃掉体验

RAG 系统有个经典问题:检索再准,LLM 也可能生成错误答案(幻觉)。我的方案(F3)是生成后做一次忠实度自检——把答案拆成一条条论断,逐条判断有没有被检索上下文支撑,不忠实用更严格的 prompt 重生成。

非流式接口下这很美好:忠实度 0.986,幻觉率压到很低。

然后我把它接到流式路径上,问题立刻出现:**裁判需要完整答案才能判,而流式是一个 token 一个 token 出的。** 朴素接法只有一种——

```
非流式整段生成 → 跑裁判 →(不忠实则重生成)→ 成品一次性吐给用户
```

首 token 时延(TTFT)≈ 完整生成时延 + 裁判时延。实测 full 模式 +1.8s。用户干等好几秒才看到第一个字——**流式的全部意义没了**。质量特性把体验特性吃掉了。

## 投机:先交付,后校验

计算机系统里有个老思路叫投机执行:先假设结果可用、立刻交付,事后校验,赌错了再纠正。CPU 分支预测这么干,数据库乐观锁这么干。我把它搬到流式生成上(F8):

```
① 逐 token 立刻流给用户      ← 赌它是忠实的
② 流结束,拿完整答案跑裁判    ← 校验在流末,不阻塞首屏
③ 判不忠实 → 严格重生成,
   追加一个 correction 事件   ← 赌输才付的成本
④ final 事件带忠实度元信息
```

打个比方:朴素做法像**录播新闻**——念完、审完、再播,稳妥但你得等;投机流式像**直播**——边念边看,审核员同步盯着,真念错了插播一条"更正:刚才那条应为……"。

代码骨架很小:

```python
def speculative_faithful_stream(*, stream_fn, question, context, checker, regen_fn, deadline, ...):
    full_answer = ""
    for token in stream_fn():                      # ① 立刻流
        full_answer += token
        yield {"type": "token", "data": token}

    if checker is None:                            # 降级:F3 关则直接放行
        yield {"type": "final", ...}
        return

    # ②③ 流末自检 + 有界重生成(与阻塞路径共用同一循环体)
    answer, faithful, score, regenerated = regen_until_faithful(
        checker, question, context, full_answer,
        produce_fn=regen_fn, max_regen=1, deadline=deadline,
        on_regen=lambda c: corrections.append(c),
    )
    for correction in corrections:
        yield {"type": "correction", "data": correction}   # 赌输:插播更正
    yield {"type": "final", "data": {"answer": answer, "faithful": faithful, ...}}
```

## 这笔账为什么划算

关键在于概率:**绝大多数答案本来就是忠实的**(实测重生成率 1.7%-3.4%)。

- 97% 的请求:用户白赚一个秒开体验,裁判的 ~1s 完全不可见;
- 3% 的请求:多付一次重生成,前端收到 correction 事件替换答案——最终停留在页面上的仍是校验过的版本。

反过来看朴素做法:为了消灭这 3% 的错误窗口,让 100% 的用户在看见任何字之前多等 ~1s。**让所有人陪小概率风险等待,是最差的权衡。**

三个工程细节决定它是健壮的还是玩具:

1. **单一事实源**:裁判和生成器看的是**同一份格式化上下文**。早期版本裁判自己截断上下文,导致答案明明忠实却被判不忠实、白白重生成(误触发 11 次);对齐后误触发归零。校验闭环的前提是裁判标准和生成依据严格一致。
2. **有界 + 熔断**:最多重生成一次(`max_regen=1`),且受查询级延迟预算约束——超预算直接跳过重生成,带着 `faithful=False` 标记如实返回。**绝不无限循环,绝不伪装成已校验。**
3. **降级透明**:裁判崩了/输出解析失败 → `faithful=None` 放行。系统宁可承认"未知",也不谎报"已校验"。

## 诚实地讲代价

这个设计有一个明码标价的缝隙,我不打算美化它:

**用户看到完整答案的那一刻,校验还没开始。** 我的评测集答案很短(中位数 20 字),用户 1-2 秒读完,而裁判要 ~1 秒且从流末才开始——所以短答案下,用户读完、裁判还没判完是常态。长答案(产品里 200 字的完整回答)则相反:阅读 30 秒远大于裁判 1 秒,校验完全藏在阅读时间里。

精确地说,投机流式的保证是:**"停留在页面上的最终版本经过校验,且你几乎不用为校验等待"**——它不保证"你看到的第一眼经过校验"。那 3% 概率、约 1 秒的错误曝光窗口,是这个设计的真实价格。能不能接受取决于产品:对聊天产品,答案闪过一秒后被更正替换,体验是连续的;对医疗/金融场景,这个窗口可能就不能接受——那时候你该回到录播,老老实实付那 1 秒。

还有一个常被问的:为什么不做成边流边判?三点——半句话拆不出完整论断,判了也是误判;一次调用判全部论断比多次调用便宜;流耗尽即调裁判,中间没有可压缩的串行等待。

## 结语:性能优化常常不是把活干快,而是换个时间干

投机流式没有让任何一步变快:生成还是那个生成,裁判还是那个裁判,3% 的情况下总工作量甚至增加了。它只是**把校验从"挡在门口"挪到"跟在身后"**——挪到用户注意力不在"等待"上的时间段里。

这也是我在这个项目里反复用到的一个判断:质量与体验冲突时,先问"这个冲突是物理定律,还是顺序问题"。F3 和流式之间没有任何物理矛盾——裁判不需要在首 token 之前完成,是我们自己把它排在那里的。
