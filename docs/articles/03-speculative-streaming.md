# 先吐为敬:我给 RAG 加了一个会"插播更正"的直播员

> 给流式 RAG 加忠实度校验,最自然的做法会杀死流式体验本身。这篇讲一个从 CPU 分支预测偷来的思路:先按"它是对的"交付,事后校验,错了再更正。重点不是它多聪明,是它明码标价的那个代价——大约 3% 的情况下,用户会先看到一秒钟未经校验的答案。

## 一、你加了一个正确的功能,然后体验死了

故事从一个很常见的需求开始:RAG 系统会幻觉——检索再准,LLM 也可能生成文档里没有的内容。所以我做了一个忠实度校验(F3):答案生成后,把它拆成一条条论断,逐条检查有没有被检索上下文支撑;不忠实,就用更严格的提示词重生成一遍。

非流式接口下,它工作得很好:忠实度稳定在 0.98 以上。

然后我把它接到流式路径上。流式的全部意义,是那个**逐字蹦出来的光标**——用户 0.5 秒看到第一个字,感觉系统是"活的"。而忠实度校验有一个内在的脾气:**它需要完整的答案才能判断。** 半句话拆不出论断,判了也是乱判。

于是唯一"自然"的接法是这样的:

```
非流式整段生成(3s) → 跑校验(1s) → 不忠实就重生成 → 把成品一次性吐给用户
```

首字时延 ≈ 完整生成时延 + 校验时延。实测 full 模式 +1.8s。用户干等四五秒,光标纹丝不动,然后"哗"地一下全出来了——**你花了很大力气做的流式,等于没做。**

我加了一个质量上正确的功能,然后它把体验杀死了。

## 二、这个矛盾是物理定律,还是排列问题?

卡住的时候,我喜欢先问一个问题:**眼前的冲突是物理定律,还是我自己把工序排错了?**

校验必须在生成之后——这是物理定律,答案不完整没法判。但校验必须在**用户看到答案之前**吗?重新读一遍需求,我发现没有任何一条这么说。是我想当然地把"校验"排在了"交付"前面,因为在大多数系统里,质量检查就是门卫:不过检,不放行。

但门卫模型不是唯一选择。计算机系统里有个老思路,叫**投机执行**:先假设一个结果,立刻用它往下走,事后验证,错了再纠正。CPU 的分支预测每天都在干这件事——遇到条件跳转,不等结果,猜一个方向继续执行,猜错了把流水线冲掉重来。猜对的概率很高,所以平均速度大幅提升;猜错的代价被隔离在一个可回滚的窗口里。

把这个思路映射到流式 RAG:

| CPU 分支预测 | 投机流式 |
|---|---|
| 猜一个分支方向 | 假设答案是忠实的 |
| 立刻沿猜测执行 | 立刻逐 token 流给用户 |
| 解析完成后验证 | 流结束后跑忠实度校验 |
| 猜错 → 冲刷流水线 | 不忠实 → 插播更正事件 |
| 绝大多数时候猜对 | 绝大多数答案本来就忠实 |

最后一行是这笔账成立的前提,我的系统里它成立:重生成触发率 1.7%-3.4%,也就是说 **97% 的答案本来就是忠实的**。让 97% 的请求陪 3% 的风险排队等校验,是我能想到的最差权衡。

## 三、设计:三个事件、一份契约、一条熔断

实现骨架很小:

```python
def speculative_faithful_stream(*, stream_fn, question, context, checker, regen_fn, deadline, ...):
    full_answer = ""
    for token in stream_fn():                      # ① 立刻逐字流
        full_answer += token
        yield {"type": "token", "data": token}

    # ② 流末校验 + ③ 有界重生成(与阻塞路径共用同一循环体)
    try:
        answer, faithful, score, regenerated = regen_until_faithful(
            checker, question, context, full_answer,
            produce_fn=regen_fn, max_regen=1, deadline=deadline,
            on_regen=lambda c: corrections.append(c),
        )
    except Exception as e:                          # 校验崩了也不让流死掉
        answer, faithful, score, regenerated = full_answer, None, 0.0, False
    for correction in corrections:
        yield {"type": "correction", "data": correction}
    yield {"type": "final", "data": {...}}          # 无论如何都发 final
```

三个事件:`token`(逐字)、`correction`(不忠实时的更正答案,前端替换已显示内容)、`final`(最终答案 + 忠实度元信息)。前端协议很简单:正常收 token,见到 correction 就替换,见到 final 就收尾。

但骨架之外有三个决定,才是它从"demo"变成"能用"的分界线:

**决定一:单一事实源。** 裁判和生成器必须看**同一份**格式化上下文,由函数参数显式传递。这不是洁癖——早期版本里裁判自己截断上下文(前 5 篇×400 字),结果答案的依据落在第 6 篇时,裁判看不到 → 判不忠实 → 白白重生成。校验闭环的前提是"判官的依据"和"作者的依据"严格同址同源,差一个字都会制造假阳性。

**决定二:有界纠正。** `max_regen=1`,最多重生成一次,不做"直到忠实为止"的循环。无限循环是用延迟的不确定性换质量的幻觉——而严格提示词的一次重生成通过率本来就很高。一轮后仍不忠实,就带着 `faithful=False` 的标记如实返回。**系统宁可承认没救回来,不假装救回来了。**

**决定三:熔断,而且两条路径同一个循环体。** 校验和重生成受查询级延迟预算约束(超预算跳过,标"未校验");流式路径和阻塞路径共用 `regen_until_faithful` 这一个函数——行为一致性由代码结构保证,不靠"两处各写一遍并保持同步"这种人肉契约。

## 四、这笔账:谁赚了,谁付了

先说赚的:97% 的请求,用户白赚一个秒开体验,裁判的那 1 秒完全不可见——它在后台跑,跑完发个 final,用户甚至不知道有这回事。3% 的请求多付一次 LLM 调用,前端收到更正,最终停留在页面上的仍是校验过的版本。

但我要把付的部分讲到底,因为这一半几乎没人讲:

**代价一:一个真实的未校验窗口。** token 流完的那一刻,校验才刚开始。短答案(我的评测集中位数 20 字)用户一两秒就读完了,裁判要 1 秒左右才出结果——**所以"用户读完、裁判还没判完"是常态,不是意外**。如果那 3% 恰好发生,用户已经看到了错误答案约一秒钟,然后更正插播。它只是"闪过",不是"留下",但闪过也是发生。

这里我要诚实地修正一个我自己早期讲错过的点:我一度画过一张时序图,暗示"校验藏在用户阅读时间里"。这只对长答案成立(200 字的回答读 30 秒,校验 1 秒完全被吸收);对短答案不成立。投机流式的准确保证是:**"停留在页面上的最终版本经过校验,且你几乎不用为校验等待"**——它不保证"你看到的第一眼经过校验"。

**代价二:它的适用域是有边界的。** 对话产品、搜索问答、知识助手——答案闪过一秒再被更正,体验是连续的,这个权衡非常划算。但医疗、金融、合规场景,那一秒的错误曝光可能就不能接受。所以它是一个**开关**(`use_speculative_streaming`),关掉就回到"校验通过才交付"的阻塞路径,用 1 秒首字时延换零窗口。选哪个是产品决策,不是技术优劣——我的工作是把两个选项都做好,并把各自的价签贴清楚。

还有一个常被问的:为什么不做成边流边判?三个理由叠加——半句话拆不出完整论断(判了也是误判);一次调用判全部论断,比流到一半判一次、结束再判一次便宜;流耗尽即调裁判,中间没有可压缩的串行空隙。它不是没想到,是算完账放弃了。

## 五、性能优化常常不是把活干快,而是换个时间干

回头看,投机流式没有让任何一步变快:生成还是那个生成,校验还是那个校验,3% 的情况下总工作量甚至增加了。它只做了一件事——**把校验从"挡在门口"挪到"跟在身后"**,挪到用户注意力不在"等待"上的时间段里。

这是我在这个系统里反复用到的一个判断:质量和体验冲突时,先问那是物理定律还是排列问题。F3 和流式之间没有任何物理矛盾——裁判从来不需要在首 token 之前完成,是我自己把它排在那里的。

而比这个技巧更重要的,是那个"明码标价"的习惯。每一个质量与体验的权衡,都该有一个写出来的价签:3% 的概率、1 秒的窗口、哪些场景不适用。**藏起来的代价不会消失,只会在某个凌晨三点变成事故,而贴着价签的代价只是一个决策。**

先吐为敬,验不过再补正——这不是对质量打折扣,是给质量换了一个更懂用户体验的交付时间。
