# 系统设计面试指南

## 面试框架

系统设计面试通常 45 分钟，考察候选人将模糊需求转化为完整技术方案的能力。

### 四步法
1. **需求澄清（5min）**：确认功能需求、非功能需求、规模估算
2. **高层设计（10min）**：画出核心组件和数据流
3. **深入设计（20min）**：选择关键模块展开（存储、缓存、一致性等）
4. **权衡讨论（10min）**：瓶颈分析、扩展方案、故障处理

## 规模估算（Back-of-envelope）

| 指标 | 数值 |
|------|------|
| QPS（读） | 日活 × 每用户请求数 / 86400 |
| QPS（写） | 通常为读的 1/10 ~ 1/100 |
| 存储/天 | 日新增记录 × 每条大小 |
| 带宽 | QPS × 平均响应大小 |
| 缓存大小 | 热数据 ≈ 总量 × 20%（二八定律） |

### 常见数量级
- 1 天 ≈ 10^5 秒
- 1 年 ≈ 3 × 10^7 秒
- 1 KB = 10^3 B, 1 MB = 10^6 B, 1 GB = 10^9 B, 1 TB = 10^12 B

## 核心组件选型

### 数据库选择
- **关系型（MySQL/PostgreSQL）**：强一致性、复杂查询、事务
- **文档型（MongoDB）**：灵活 Schema、嵌套结构、快速迭代
- **KV 存储（Redis/DynamoDB）**：低延迟、简单访问模式
- **图数据库（Neo4j）**：社交关系、推荐网络
- **时序数据库（InfluxDB/TimescaleDB）**：监控指标、IoT 数据
- **搜索引擎（Elasticsearch）**：全文检索、日志分析

### 缓存策略
- **Cache-Aside**：应用层管理，先查缓存再查 DB（最常用）
- **Write-Through**：写入时同步更新缓存
- **Write-Behind**：异步批量写回 DB，高吞吐但有丢失风险
- **缓存穿透**：布隆过滤器 / 空值缓存
- **缓存雪崩**：过期时间加随机偏移
- **缓存击穿**：互斥锁 / 永不过期 + 异步更新

### 消息队列
- **Kafka**：高吞吐、日志流、事件溯源
- **RabbitMQ**：灵活路由、任务队列
- **RocketMQ**：事务消息、延迟消息
- **Pulsar**：多租户、存算分离

## 经典设计题

### 短链系统（URL Shortener）
- 核心：长链 → 短码映射（Base62 编码 / 自增 ID）
- 存储：KV 存储（短码 → 长链）
- 优化：布隆过滤器去重、302 重定向、CDN 缓存
- 扩展：分布式 ID 生成器（Snowflake）

### Feed 流（Timeline）
- **推模式（Fan-out on write）**：发布时写入所有粉丝收件箱，读快写慢
- **拉模式（Fan-out on read）**：读取时聚合关注人动态，写快读慢
- **推拉结合**：大 V 用拉，普通用户用推

### 秒杀系统
- 前端：按钮防抖、答题验证、CDN 静态化
- 网关：限流（令牌桶）、黑名单
- 服务：库存预热到 Redis、Lua 原子扣减
- 异步：MQ 削峰、订单超时取消
- 兜底：熔断降级、兜底页

### 即时通讯（IM）
- 连接层：WebSocket 长连接、心跳保活
- 消息可靠性：ACK 机制、消息去重（client_msg_id）
- 存储：写扩散（群消息）vs 读扩散
- 已读回执、消息漫游、离线推送

## 分布式理论

### CAP 定理
分布式系统最多同时满足两个：
- **C（一致性）**：所有节点看到相同数据
- **A（可用性）**：每个请求都能得到响应
- **P（分区容错）**：网络分区时系统仍能运行

网络分区不可避免，所以实际是 CP 或 AP 的选择。

### 一致性模型
- 强一致性：Raft / Paxos（etcd、ZooKeeper）
- 最终一致性：Dynamo 风格（Cassandra、Riak）
- 因果一致性：COPS

### 负载均衡
- L4（传输层）：LVS、F5、NLB
- L7（应用层）：Nginx、HAProxy、ALB
- 算法：轮询、加权、最少连接、一致性哈希

## 高可用设计

### 高可用核心方案
- **冗余部署**：多副本、多机房（同城双活 / 异地多活），消除单点故障
- **负载均衡**：流量分发到多个实例，避免单节点过载
- **故障转移（Failover）**：自动检测节点故障并切换到健康节点（如 Redis Sentinel、MySQL MHA）
- **熔断降级**：当下游服务错误率超阈值时自动熔断，返回兜底响应，防止级联故障（Hystrix、Sentinel）
- **健康检查**：定期探测服务实例存活状态，不健康实例自动摘除
- **灰度发布**：新版本先对小流量验证，异常时快速回滚

### 可用性指标
- 99.9%（三个9）：年停机 < 8.76 小时
- 99.99%（四个9）：年停机 < 52.6 分钟
- 99.999%（五个9）：年停机 < 5.26 分钟

## 限流算法

### 四种经典限流算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口 | 将时间划分为固定窗口，窗口内计数不超过阈值 | 实现简单 | 窗口边界可能出现2倍突刺 |
| 滑动窗口 | 将固定窗口细分为多个小格子，统计滑动范围内的请求数 | 平滑，避免边界突刺 | 实现稍复杂 |
| 漏桶算法 | 请求以恒定速率处理，超出容量的请求排队或丢弃 | 流量绝对平滑 | 无法应对突发流量 |
| 令牌桶算法 | 以恒定速率向桶中放入令牌，请求需获取令牌才能通过 | 允许一定程度的突发流量 | 实现较复杂 |

### 限流实践
- **网关层限流**：Nginx（limit_req）、Kong、Spring Cloud Gateway
- **服务层限流**：Sentinel、Hystrix、Guava RateLimiter
- **分布式限流**：Redis + Lua 实现集群级限流
- **自适应限流**：根据系统负载（CPU、RT）动态调整阈值
